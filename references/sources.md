# Work sources and safety

Read this reference when collecting content material or grounding a draft in project evidence.

## Source order

Prefer evidence that already exists:

- GitHub commits, pull requests, releases, README changes, and demos
- Linear issues for Steven's personal repositories and projects
- completed Codex tasks and their final summaries
- Notion decisions, observations, project notes, and Content Inbox entries
- Calendar sessions as context for when work happened

Plane is only for Resorsi work. Treat Plane and other client material as private unless Steven explicitly selects material for public use. Convert approved private work into a generalized pattern and remove customer names, credentials, private URLs, internal metrics, and unreleased commercial details.

Software records what happened. Steven owns the meaning. When it changes the story, ask why it mattered, what surprised or frustrated him, what he did next, and what must stay private. Keep his answer separate from generated copy.

## Meaningful evidence

Keep events with at least one of these signals:

- a decision with a real tradeoff
- a problem other people recognize
- a failed attempt or changed mind
- visible proof of progress
- feedback that changed the work
- a result that contradicted the expectation

Skip dependency bumps, formatting-only commits, routine status changes, and raw command history unless they support a larger story.

## Voice / Swipe File

The Notion **Voice / Swipe File** is a curated library of public post examples. It is reference material for structure, pacing, framing, and payload choice; it is not evidence for factual claims in Steven's drafts.

When Steven asks to use saved X bookmarks as examples:

- select the named bookmark folder first; do not use the undifferentiated Bookmarks feed
- use the `Tweets` folder only when that is the folder Steven named
- add only examples with a clear reusable pattern, deduplicated by canonical post URL
- preserve author, platform, pattern, and a tentative reason the example is useful; do not claim to know why Steven saved it
- do not automatically turn every bookmark into a database row or a durable voice rule

Fetch the live Swipe File schema before writing. Update `references/voice.md` only after a preference repeats across multiple examples, published work, or Steven's explicit direction.

## Proof-to-post filter

Proof beats positioning. Real work beats a manufactured idea. For each candidate, identify:

- what happened
- what shipped or broke
- where the evidence lives
- why somebody might care
- the reusable pattern

If anyone working in AI could have written the material without Steven's evidence, keep it as a seed or reject it. For private work, keep only the generalized pattern and remove the identifying case. Never infer emotions, motivations, authority, or outcomes from software records.

Fetch the live data source before every write because identifiers, properties, and allowed values may change. Treat the IDs and state names above only as discovery hints. Adapt the concepts below to the live schema rather than creating properties blindly.

Notion owns mutable content evidence. It is not a task list or a second publishing service. `Shipped proof` is a content type, not a lifecycle state.

Use properties for lifecycle and searchable metadata. Keep long evidence, raw human context, draft history, and review notes in the page body. A record can remain `Raw` or `Seed` without complete human context. Move it to `Approved` only when `Human context ready?` and `Safe to share?` are explicit.

For shipped proof, preserve the artifact, project, evidence URL or local path, outcome, public or private classification, and reusable pattern. For drafting feedback, preserve the original draft in the page body and the exact approved copy in its property. Record Steven's changes, rejection or archive reason, platform, publisher item ID, review URL, schedule or publication time, public URL, and outcome when those values exist.

## Content assets

Before copying a local screenshot, video, or other asset, discover and verify the current canonical content destination. Do not treat an old Drive folder ID as current. Reuse an existing asset when its source or checksum shows that it is already stored. Preserve the source, capture date, canonical asset link, and a short statement of what the asset proves in the Content Inbox.

Never store credentials, secrets, private URLs, or unsafe client material. A local path is evidence only while it remains accessible; use the verified canonical destination when durable capture was requested.
